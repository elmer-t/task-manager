# Task Manager — v1 spec (locked)

**Status:** Locked, ready for implementation sessions.
**Date:** 2026-07-15.
**Source:** [Wayfinder map: Windows task manager v1 spec & stack (#1)](https://github.com/elmer-t/task-manager/issues/1). Every decision below traces to a closed map ticket (#2–#6) or ADR-0001.

This is the single document an implementation session opens. Terms in **bold-italic** on first use are defined in [`CONTEXT.md`](../../CONTEXT.md).

## 1. What v1 is

A personal, daily-use Windows task manager, Fluent-styled, that is also a vehicle for learning the WinUI 3 / modern-native-Windows stack. Pragmatic choices win; distribution barely matters (running a local build is enough).

v1 does exactly this and no more:

- Three views — **_Apps_**, **_Background processes_**, **_Services_** — switched by a left rail.
- System-wide **CPU** and **memory** graphs, always visible.
- Per-process **CPU %** and **memory** columns.
- **Kill process** ("End task") as the *only* action. Everything else is read-only.

## 2. Non-goals (out of scope for v1)

- Disk / network / GPU performance graphs — CPU + memory only.
- Startup-app management.
- Installer / auto-update — a local build is enough.
- Service start / stop / restart — the Services view is **view-only**.

These are fixed scope boundaries, not backlog. They return only if a future effort redraws the destination.

## 3. Tech stack (ADR-0001)

| Concern | Choice |
| --- | --- |
| Language | C# |
| UI framework | WinUI 3 / Windows App SDK |
| Charting | LiveCharts2 (SkiaSharp-based, MVVM/XAML-idiomatic) |
| Data access | Raw Win32 via **CsWin32** source-generated P/Invoke |
| Architecture | Single process — counters polled and charts painted in-process; no IPC boundary |

Fluent styling is first-party: real WinUI controls, `MicaBackdrop` (Mica, with WinUI's automatic fallback when the OS suppresses it), automatic system dark/light. No visual designer — XAML is authored by hand (Hot Reload only).

Rationale and rejected alternatives (WPF fallback, Avalonia, Tauri/Electron; LiveCharts2 vs ScottPlot 5 vs hand-rolled Win2D) live in [ADR-0001](../adr/0001-v1-tech-stack.md).

## 4. Data sources & the polling model

All data comes from plain Win32, polled on a single **1 Hz** tick. This is the design point the whole spec is built around (see §5).

| Need | API |
| --- | --- |
| Process list (names, PIDs) | `CreateToolhelp32Snapshot` — no per-process handle needed |
| App vs. Background classification | `EnumWindows` → `GetWindowThreadProcessId` → `IsWindowVisible`, excluding owned windows, `WS_EX_TOOLWINDOW`, and DWM-cloaked (`DWMWA_CLOAKED`) windows (see §7) |
| Services + states + hosting PID | `OpenSCManager` + `EnumServicesStatusEx(SC_ENUM_PROCESS_INFO)` |
| System CPU % | `GetSystemTimes` delta between ticks |
| System memory | `GlobalMemoryStatusEx` (with `GetPerformanceInfo` for commit charge) |
| Per-process CPU % | `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `GetProcessTimes` delta |
| Per-process memory | `GetProcessMemoryInfo` → `PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize` (**Private Working Set**, Win10/11 22H2+), matching Task Manager's Memory column |
| Kill | `OpenProcess(PROCESS_TERMINATE)` + `TerminateProcess` |

Full API survey with Microsoft Learn citations: [`docs/research/windows-data-sources.md`](../research/windows-data-sources.md) (on branch `research/windows-data-sources`).

### Elevation & graceful degradation

The **read path requires no elevation.** The app runs un-elevated by default.

- **No admin needed:** process enumeration, window-based classification, service enumeration with states, system CPU/memory, per-process CPU/memory *for your own processes*, killing *your own* processes.
- **Needs admin (`SeDebugPrivilege`):** per-process CPU/memory and End task for *other users'* and *service* processes.
- **Never works, even elevated:** opening System, CSRSS, or protected processes.

Degradation rules (never a hard error, never pre-blocking):

- Process list stays **complete** — toolhelp needs no handles.
- A row whose `OpenProcess` fails shows **blank CPU/memory cells**.
- A service the caller can't `SERVICE_QUERY_STATUS` is **silently omitted**.
- Both system graphs always work.
- End task on an inaccessible process surfaces the elevate flow in §8 — it is *not* pre-disabled.

## 5. Refresh cadence & history (ticket #6)

- **Sampling:** once per second (**1 Hz**) for every counter — process table, service states, and both system graphs.
- **Graph history:** a rolling **60-second** window.
- **Fixed:** no user-facing update-speed or history setting in v1.
- **Self-overhead budget:** the monitor's own cost is one toolhelp snapshot plus N cheap handle queries per tick — negligible. Target: the app should not itself be a noticeable row in its own CPU column under normal load. Do not add per-tick work (e.g. PDH per-process instances, WMI round-trips) that would inflate this; those were considered and rejected in #3.

## 6. UI layout (ticket #5 — "Variant A")

```
┌───────────┬─────────────────────────────────────────────┐
│           │  ┌─────────────┐  ┌─────────────┐            │  ← graph strip: PINNED
│  ▸ Apps   │  │  CPU  ~~~~~  │  │  Memory ~~~ │            │    (fixed row)
│  ▸ Backgr │  └─────────────┘  └─────────────┘            │
│  ▸ Servic │  ─────────────────────────────────────────── │
│           │  Name              CPU%      Memory           │  ← process list:
│           │  ▸ chrome.exe       12.4%     842 MB          │    SCROLLS beneath
│  [rail]   │  ▸ ...                                        │    the pinned strip
└───────────┴─────────────────────────────────────────────┘
```

- **Left rail:** WinUI `NavigationView` switching **Apps / Background processes / Services**.
- **Graph strip:** two cards — CPU and memory — **pinned** to the top of the content area. The process list scrolls beneath it; the graphs stay visible at all times. (WinUI: a `Grid` with a fixed row for the strip and a scrolling row for the list.)
- The graph strip shows the **system-wide** CPU and memory for the whole machine, identical across all three views.

### Columns

| View | Columns |
| --- | --- |
| Apps | **Name** (icon + label) · **CPU %** · **Memory** |
| Background processes | **Name** (icon + label) · **CPU %** · **Memory** |
| Services | **Name** (display name) · **Description** · **Status** (Running / Stopped pill) |

Numeric columns are right-aligned with tabular figures and usage-heat emphasis. The Services view is view-only (§2).

## 7. App vs. Background classification (ticket #6)

A process is classified **App** if it owns **at least one** top-level window that is *all* of:

1. visible (`IsWindowVisible`),
2. not a tool window (`WS_EX_TOOLWINDOW`),
3. unowned (no owner via `GetWindow(GW_OWNER)`), and
4. not DWM-cloaked (`DWMWA_CLOAKED`).

Otherwise it is a **Background process**.

Edge cases resolve by this rule as-is — **simple heuristic, imperfections accepted** (no AUMID / packaged-app special-casing in v1):

- **Multi-window process** → one App row; the qualifying-window test naturally dedupes to a single process entry.
- **Suspended UWP / packaged app** → its window is DWM-cloaked, so it falls to **Background** (as it reads to a user).
- **Tray-only app** (no qualifying window, just a notification-area icon) → **Background**.

This may not pixel-match Windows Task Manager's "Apps" grouping in every case; the behavior is defined and cheap, which is what v1 wants.

## 8. Kill-process UX (tickets #5 + #6)

**Gesture (deliberate select-then-kill):** select a process row, then invoke **End task** via either the command-bar button (top-right of the list) or the right-click context menu. There is no zero-friction inline kill.

**Confirmation:** every End task shows a Fluent `ContentDialog` first — e.g. *"End &lt;process&gt;? Unsaved data may be lost."* with **End / Cancel**. Confirmation is unconditional (apps, background, and service-hosting processes alike).

**On success:** the process terminates; the row disappears on the next tick.

**On failure (Access Denied — protected / other-user / service process):** show a Fluent error dialog explaining elevation is required, offering a **"Restart as administrator"** action that relaunches the whole app elevated (UAC prompt via the `runas` verb). The app never pre-disables End task per row and never probes terminate-rights up front — it attempts, then surfaces the elevate affordance, mirroring Task Manager (#3).

## 9. Requirement checklist (for implementation sessions)

- [ ] WinUI 3 app shell with `NavigationView` (Apps / Background / Services) and `MicaBackdrop`, following system dark/light.
- [ ] 1 Hz polling loop driving all data; rolling 60 s buffers for the two system graphs.
- [ ] CsWin32 bindings for: `CreateToolhelp32Snapshot`, `EnumWindows`/`GetWindowThreadProcessId`/`IsWindowVisible`/`GetWindow`/`DwmGetWindowAttribute`, `EnumServicesStatusEx`, `GetSystemTimes`, `GlobalMemoryStatusEx`/`GetPerformanceInfo`, `OpenProcess`/`GetProcessTimes`/`GetProcessMemoryInfo` (`PROCESS_MEMORY_COUNTERS_EX2`), `TerminateProcess`.
- [ ] App/Background classifier per §7.
- [ ] Two LiveCharts2 scrolling filled-line series (CPU %, memory) pinned at top.
- [ ] Process list (Name · CPU % · Memory) per view; Services list (Name · Description · Status pill).
- [ ] End task: select-then-kill, unconditional confirm dialog, blank-cell degradation, error + "Restart as administrator" on Access Denied.
- [ ] Self-overhead stays negligible (no PDH-per-process / WMI on the hot path).
